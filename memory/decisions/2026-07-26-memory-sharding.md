# 메모리 구조 — monolith 폐기, 인덱스 + 1결정 1파일

**문제 제기(유저)**: 결정이 쌓일수록 md가 커지는데, **컨텍스트에 다 로드할 수 있는지**가 걱정된다. 토큰 비용이 아니라 물리적 적재 가능성의 문제.

## 실측으로 확인한 것

- 당시 메모리 전체 = **312줄 / 20,379자** (`portfolio.md`가 80줄 / 10블록, 결정 1건 = 8줄).
- **10만 줄 시나리오는 오지 않는다** — 결정 12,500건, 현 페이스로 약 62년치.
- **하지만 진짜 천장은 훨씬 낮다.** 줄당 약 60~70토큰 → 상시 로드에 쓸 만한 현실 예산은 창의 10% 수준, 즉 **1M 창에서 ~1,500줄 / 200K 창에서 ~300줄**. 성장률이 연 1,000~1,600줄이므로 **1~2년이면 예산 초과**(200K 기준으론 이미 초과).
- Read 툴은 기본 2,000줄까지만 읽는다 → 큰 파일은 **애초에 통째로 안 읽힌다.** "다 로드"는 지금 파일이 작아서 우연히 성립하던 것.

## 결정

**압축(요약) ❌ / 계층화 ⭕.** 요약은 이 시스템이 지키려는 바로 그것(이유·함정 디테일)을 먼저 버리므로 자해다. 대신 **총량과 상시 로드량을 분리**한다.

- **1결정 = 1파일**, `memory/decisions/YYYY-MM-DD-<slug>.md`. frontmatter(`name`/`description`/`metadata`) + 본문.
- **`memory/decisions/README.md`가 인덱스** — 결정 1건 = 한 줄. **세션에서 항상 읽는 건 이 인덱스뿐**이고, 본문은 필요할 때만 연다.
- 열린 항목은 인덱스 최상단에 별도 섹션으로 노출.
- **아카이브 트리거**: 인덱스가 **300줄**을 넘으면 오래된 확정 결정을 `archive/YYYY-H{1,2}/`로 강등하고, 인덱스엔 `"N건 — grep으로 조회"` 한 줄로 접는다. → 상시 로드분이 **상수로 고정**되고 총량은 얼마가 되든 무관해진다.

**이유**: 총량을 5만 줄로 줄여도 여전히 못 읽는다. 반면 인덱스+아카이브는 100만 줄이어도 300줄만 읽는다 — 자릿수가 다른 해법. 회사 camfit 네이티브 메모리(33파일 + `MEMORY.md` 인덱스)와 CPF가 대규모로 안 터지는 이유도 양이 적어서가 아니라 **전부 로드하지 않아서**다.

**동시 정리**: `(기존) 스택 시그니처`·`(기존) 포트 레지스트리` 두 블록(863자)은 `CLAUDE.md`에 이미 규칙으로 승격돼 있는데 로그 쪽 원본을 안 내려 **정본 이중화** 상태였다 → 본문 제거, 인덱스에 "규칙으로 승격됨" 포인터만 남김. (원문은 git 히스토리에 있음.)

**부수 원칙**: 반복되는 결정이 규칙으로 굳으면 `CLAUDE.md`로 **승격**하고 로그엔 포인터만 남긴다.

**상태**: 확정 · 적용 완료(10블록 → 9파일 + 인덱스).
