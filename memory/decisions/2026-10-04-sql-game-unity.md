# SQL 학습 게임을 Unity로 가볍게 만든다

**출처**: ChatGPT 기획 대화 "SQL 게임 기획 작성" (https://chatgpt.com/share/6ac21eea-b320-83ee-b514-f7131feac0f6, 2026-10-04 열람). 대화 중 여러 번 뒤집혔으므로 아래는 **최종 상태**만 적는다.

**결정**

- **무엇**: 작은 스타트업(처음엔 8명, 2026-10-11에 6명으로 줄임)의 첫 데이터 분석가가 되어, 팀원들의 데이터 요청을 SQL로 해결하며 회사와 함께 성장하는 게임. "SQL 문제를 푼다"가 아니라 "업무 요청을 쳐낸다".
- **엔진**: Unity 6 + C# + 2D + UI Toolkit + 내장 SQLite. 서버·계정·클라우드 세이브 없음(전부 로컬).
- **플랫폼**: 모바일 세로 화면이 정본. Steam은 나중에 될 수도 있는 확장판 — 당장은 안 키운다.
- **범위**: "가볍게". 사무실 돌아다니기·경영 시뮬레이션·Endless·스토리 엔딩은 첫 버전에서 뺀다. 회사 성장은 진행도의 시각화일 뿐.
- **첫 목표(vertical slice)**: NPC 한 명의 요청 → SQL 작성 → 실제 DB 실행 → 요구사항 판정 → NPC 반응 → 자동 저장. 그 다음이 "6명 회사 + 테이블 4개 + SQL 개념 3개 + 업무 15개"로 휴대폰 30분 플레이 검증.
- **판정**: 정답 SQL과 문자열 비교하지 않고 결과 집합·DB 상태로 검증. "실행은 되지만 요구사항은 틀린" 쿼리가 핵심 재미.
- **세이브**: 커리어는 자동 저장(수동 로드 없음), DB는 별도 스냅샷/복구(DROP·WHERE 없는 UPDATE 사고 대비).
- **아트**: 색감은 블루아카이브+데이브 더 다이버의 청량함(미소녀 아님), 캐릭터는 KUNG-FU-PIGGY 계열. 사람=손그림, 데이터=도트. DB 자체가 도트 생물 마스코트. 주인공 얼굴은 안 보임.

**이유**

- **Unity인 이유는 이 게임이 아니라 그 다음 때문**: 유저 발언 "언젠가 사이즈 큰 게임들도 만들거거든". 이 게임만 보면 Godot으로 충분하다는 게 대화의 결론이었고, Unity는 장기 학습 투자로 고른 것.
- **스택 시그니처 이탈은 의도된 것**: NestJS·Next·TS·Drizzle·PostgreSQL 어느 것도 안 쓴다. 게임이라는 장르 자체가 다르므로 부채가 아니다.
- **SQLite인 이유**: 앱에 내장 가능·서버 불필요. 가짜 파서 대신 진짜 엔진을 돌려야 학습 가치가 있다.

**함정**

- **범위 팽창이 이 기획의 기본 성향이다.** 대화가 교육게임 → 분석가 시뮬 → 회사 성장 시뮬 → Steam 정본까지 부풀었다가 유저가 직접 "모바일 정본, 크게 안 키운다"로 되돌렸다. 새 아이디어가 붙을 때마다 vertical slice에 필요한지부터 묻는다.
- **SQLite에는 ROLLUP·CUBE·GROUPING SETS가 없다**([[2026-09-08-sql-dojo-routine]]에서 같은 이유로 PostgreSQL을 골랐다). sql-dojo의 SQLD 문제를 게임 업무로 옮길 때 그 유형은 못 옮긴다. 윈도우 함수·CTE는 된다.
- **모바일에서 SQL 타이핑**이 UX의 최대 미지수. 전용 키 줄·자동완성 등 입력기를 vertical slice에서 바로 검증해야 한다.
- ~~Unity가 이 머신에 아직 설치돼 있지 않다~~ → 6000.6.4f1 설치·프로젝트 생성 완료(2026-10-04).

**상태**: 확정. 프로젝트명은 `sql-office`로 시작했다가 같은 날 **`aloha-sql`**로 바꿨다(게임 제목이 "알로하 SQL: 눌라 섬 워케이션"으로 정해져서). **기획 정본은 `aloha-sql/PLANNING.md`로 옮겼다**([[2026-07-11-planning-first]]) — 이 파일은 포트폴리오 차원의 결정(스택 이탈·이유)과 포인터만 남긴다. 게임 기획이 바뀌면 그쪽을 고친다.
